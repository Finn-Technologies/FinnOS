# FinnOS Technical and Product Audit

Snapshot: `main` at `3539a35`, 2026-07-16. This report distinguishes executed evidence from source inspection and planning text. Generated build outputs are ignored by Git and are not evidence of shipped support.

## Executive summary

FinnOS is a credible, well-tested x86-64 UEFI kernel-core prototype. It is not yet a functional OS: there is no userspace, process isolation, IPC, device model, storage, filesystem, input, networking, graphical stack, application model, package system, updater, or ARM64 executable. The strongest implementation is a deterministic early-boot chain from UEFI through private page tables, a bounded heap, xAPIC timer, and cooperative ring-0 tasks.

Level 0 is met for the x86-64 development target. Level 1 is only partial because ARM64 and production shutdown are absent. Level 2 has not started at execution level.

## Evidence and method

- Inspected all tracked source, build, test, workflow, policy, architecture, ADR, and planning trees.

- Real hardware was unavailable and no ARM64 target exists. Those results remain unknown/unsupported rather than inferred.

## Current architecture

The detailed flow is in [ARCHITECTURE.md](../../ARCHITECTURE.md). The loader reads `KERNEL.ELF` through UEFI, validates x86-64 ELF metadata, loads up to 32 segments at linked physical addresses, captures GOP/ACPI/memory-map data in protocol v2, exits boot services, and enters the kernel. The kernel builds exception state, classifies memory, creates private supervisor W^X mappings, a fixed heap, a BSP xAPIC timer, and fixed cooperative tasks. It then draws a diagnostic fill and idles.

There is no userspace, graphics startup, input path, runtime storage path, network path, or application execution path.

## Subsystem findings

### Boot and platform

UEFI, ELF loading, GOP, RSDP handoff, early COM1, kernel entry, exception setup, and QEMU exit are implemented. During this audit, executable-entry validation was corrected to require membership in one executable segment and a disjoint-segment regression test was added. The loader still inherits firmware mappings and has no relocation/KASLR/signature verification. ACPI is not parsed; IOAPIC, SMP, CPU topology, RTC, power management, shutdown, and reboot are absent.

### Kernel

Implemented foundations include bounded physical allocation, kernel-only virtual memory, fixed heap, exceptions, periodic ticks, fixed cooperative tasks, guarded stacks, and context switching. Processes, user address spaces, syscalls, blocking/wakeup, preemption, priorities, signals, IPC, handles, capabilities, resource accounting, modules, dynamic driver loading, and isolation are absent. Fatal exceptions print diagnostics and halt/test-exit; there is no crash persistence.

### Drivers and hardware

Only polling COM1, PIC masking, PIT calibration, BSP xAPIC, GOP handoff, and QEMU test exit exist. There is no device framework, PCI, USB, VirtIO, input, block, network, audio, RTC, NVMe, AHCI, Wi-Fi, Bluetooth, battery, sensors, or ARM platform support. See [HARDWARE_SUPPORT.md](../../HARDWARE_SUPPORT.md).

### Storage and filesystems

The host tool creates a FAT boot image and UEFI reads the kernel before handoff. The kernel has no block layer, partition parser, VFS, filesystem, descriptors, cache, permissions, mounts, persistence, `/dev`-like namespace, or crash recovery. Runtime storage is 0%.

### Userspace

No user binary, libc/runtime, loader, process creation, init, services, shell, utilities, users, logging service, configuration, package installer, SDK, or compatibility layer exists. Architecture documents are planning evidence only.

### Networking

No network abstraction or protocol exists, and QEMU runs with `-net none`. Ethernet, ARP/NDP, IPv4/6, ICMP, UDP/TCP, DHCP, DNS, routing, sockets, loopback, firewalling, TLS, configuration, and diagnostics are absent.

### Graphics and UI

Only GOP pixel encoding and full-screen fill exist. There is no display mode setting, renderer, acceleration, font/text, input, compositor, windows, toolkit, shell, accessibility, localization, multi-monitor, settings, file manager, terminal, login, notifications, or applications. The implementable Peony plan is in [UI_GUIDELINES.md](../../UI_GUIDELINES.md).

### Security

Current mitigations are supervisor-only mappings, W^X/NX, CR0.WP, null unmapping, guards, conservative memory classification, and Rust checks. They reduce accidental kernel corruption but provide no hostile-code boundary. All tasks are ring 0. Authentication, authorization, capability enforcement, entropy, crypto API, secret storage, secure boot, signing, sandboxing, network security, and update security are absent. See [SECURITY.md](../../SECURITY.md).

### Quality and developer experience

The single CLI, host tests, serial contracts, CI, ADRs, and strict linting are strong for this stage. Weaknesses are x86/debug hard-coding, metadata drift, no ARM/macOS CI, unpinned environments/actions, no artifacts on failure, no fuzzing/coverage/security scan, and contradictory old status documents.

## Known issues

| Severity | Issue | Evidence / effect |
|---|---|---|
| High | No user/kernel security boundary | User mappings rejected; ring-0 GDT/tasks only |
| High | No device IRQ path | Only vectors `0x40` and `0xff`; PIC fully masked |
| Medium | BootInfo and map pointers assume a trusted loader | Structural checks occur after raw pointer dereference |
| Medium | Fixed capacities can fail on larger/fragmented machines | 8 tasks, 1 MiB heap, 64 page-table pages, fixed arrays |
| Medium | Empty page-table structures are not reclaimed | Long-lived varied mappings can exhaust table pool |
| Medium | Heap lock design depends on single-core non-preemption | Not safe to carry unchanged into SMP/preemption |
| Medium | Timer is not a scheduler/wakeup timer | ISR only accounts ticks and EOI |
| Medium | ACPI pointer is not validated or parsed | Blocks topology, IOAPIC, power, and hardware discovery |
| Low | Boot protocol comments call v2 “version one” | ABI documentation mismatch |
| Low | Polling serial can wait forever and kernel reinitializes COM1 per log | Fragile diagnostics on non-QEMU hardware |

Resolved during audit: ELF entry validation previously accepted gaps between disjoint executable segments. It now checks each executable segment and has a regression test in `boot/uefi/src/lib.rs`.

## GitHub and governance

GitHub had one open issue (#16), one open PR (#17), one open milestone with five closed issues, stale status/milestone labels, no GitHub release, and recent green checks after several failed iterations on the open PR. Main-branch protection strictly requires `foundation` and `smoke`, enforces rules for admins, resolves conversations, and disallows force pushes/deletion; it requires zero approving reviews and does not require signatures or linear history. Projects V2 could not be read because the token lacks `read:project`. No GitHub resources were mutated during this audit. Proposed metadata is in [`docs/github-planning/`](../github-planning/README.md).
