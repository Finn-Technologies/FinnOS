# Drivers

> Status: Initial architectural direction
> Implementation: Bounded modern VirtIO-PCI control transport, a polled VirtIO-GPU `GET_DISPLAY_INFO` query, a five-command 2D resource/backing/transfer/scanout/flush setup, a Peony damage-driven two-command follow-up, and an owned display-buffer mapping/presentation path are implemented; no restartable userspace driver framework is complete

FinnOS prefers user-space drivers, with minimal boot-critical kernel drivers. Driver processes should be isolated and support matching, hardware-resource ownership, DMA/IOMMU considerations, interrupts, restart, suspend, and resume. Signed driver packages and a reference-hardware strategy are planned security and release concerns.

Matching policy, package format, and recovery details remain unresolved. The current tree discovers BAR-backed modern VirtIO capabilities, maps common/notify regions, programs split-ring addresses, receives a real control response, submits the bounded 2D setup, submits a follow-up transfer/flush for a Peony damage rectangle, and renders the owned display buffer before copying it to GOP. Presentation is followed by a resumable teardown sequence — `SET_SCANOUT` with `resource_id = 0`, `RESOURCE_DETACH_BACKING`, then `RESOURCE_UNREF` — and the owned pages are unmapped and released only after the device confirms `Unreffed`; any failed or timed-out command leaves the buffer owned and retained for recovery rather than guessing. The sequence is still a single-threaded polled session, not a production compositor service: device interrupts, general resource ownership/revocation, continuous presentation, hardware cursor, 3D rendering, and physical-device acceleration remain unimplemented or unverified.

Interrupt-driven completion is now represented honestly rather than assumed. The `ISR` capability is resolved into a mapped region (`FINNOS:GPU:VIRTIO_ISR_REGION` reports `present=1 bytes=4096` in both emulators), per-queue MSI-X vectors are programmed through the common `QUEUE_MSIX_VECTOR` register with read-back verification and a bounded, reusable vector allocator, and a device that exposes no ISR region is refused explicitly instead of being silently approximated by polling. The ISR read is treated as destructive — QEMU's implementation clears the register and deasserts the interrupt line as part of servicing the read — so it is sampled once per observation and the used ring remains the only authority for whether a descriptor was actually returned.

What is still missing is the platform half. ARM64 GICv2 SPI routing and a bounded single-ownership device-handler table exist, and a routed SPI is dispatched to its handler instead of being treated as fatal, but no device interrupt is raised end to end yet. x86-64 has no IOAPIC or MSI-X table, so device interrupts cannot be delivered there at all. Until a platform path raises the interrupt, the live desktop runs remain polled, and the interrupt observation is a capability the driver can consume rather than one it has been proven to receive.

The device side of that capability is now confirmed rather than assumed. PCI MSI and MSI-X capabilities are decoded from the capability chain, and the MSI-X table is located from the standard `PCI_MSIX_TABLE` dword (offset with the BAR index in the low three bits) and the entry count from the low 11 bits of message control, which stores `nentries - 1`. The emulated VirtIO-GPU device reports a three-entry MSI-X table (`FINNOS:GPU:PCI_MSIX_PRESENT=1`, `FINNOS:GPU:PCI_MSIX_TABLE_SIZE=3`), and that table size bounds the vector allocator. MSI-X entries are constructed masked and disabled, so a vector cannot fire with a partially programmed address or data value.

The ARM64 guest now programs that vector completely. The `GICv2m` frame at `0x08020000` is mapped alongside the distributor and CPU interface, its `GICD_MSI_TYPER` is read to learn the frame's own SPI window (this machine reports 64 SPIs from identifier 80), and the chosen identifier is routed in the distributor (verified: enabled, group 1, priority 128) with a matching single-ownership handler registered. The MSI-X function is then enabled in message control with mask-all cleared, because QEMU recomputes the function mask as `!enabled || masked` and initialises every function disabled and masked, and finally the table entry is written with the v2m doorbell address, the interrupt identifier as data, and the vector-control enable bit. The device-side vector register is programmed and read back, so the control queue reports `QUEUE_INTERRUPT_ENABLED`.

Delivery is still not proven, and this is stated plainly. The desktop run reports `MSI_DELIVERIES=0` — no control-queue interrupt arrives. The identifier arithmetic is the subtle part and is now explicit: `GICD_MSI_TYPER` reports the frame's *MSI window*, which QEMU derives as `base_spi + 32`, while the machine wires the frame's SPI line `n` to distributor input `frame_base + n`. The doorbell subtracts the window offset from the value written, so the value written must be the window base (80 here) and the identifier that actually reaches the distributor is the frame base (48 here). Both are computed and host-tested rather than assumed.

Two further guest-side conditions were found and fixed while isolating this. QEMU gates all signalling on the group-enable bits, so a group-1 SPI is invisible unless **both** the distributor and the CPU interface are enabled for group 1; the kernel previously enabled group 0 only. Both registers are now programmed for group 0 and group 1 and verified by readback (`GICD_CTLR=0x3`, `GICC_CTLR=0x3`), and the existing SGI self-test still passes, so the change is safe.

With the arithmetic and the group enables both correct, delivery is still absent, and the gap has been narrowed from every direction. An A/B across three different frame lines (0, 1, and 5) shows **none** latch, so it is not one disconnected line, and the doorbell values are all inside the frame's accepted window. A group A/B on the same identifier shows **neither group 0 nor group 1** delivers, which rules out group-1 signalling. A QEMU `-d int` trace of the same run shows 834 IRQs actually delivered, all of them the timer PPI continuing past the point where the doorbell is written, so the interrupt path is alive.

A final control experiment settles the remaining question. Routing a plain, machine-wired INTx line (GIC input 3, 4, and 5 are the PCIe lines on `virt`) and then setting its pending bit through the distributor's own `GICD_ISPENDR` write **also** fails to latch. The same probe confirms the distributor accepts and reflects every routing write (enabled, group 1, and priority all read back as programmed), so the guest is writing the right registers to the right distributor; only the pending and active bits stay clear. In other words, on this QEMU build and machine configuration the GICv2 distributor does not latch pending for any SPI, whether raised through the v2m MSI doorbell or written directly, while PPIs continue to arrive normally.

Chasing that result did surface a real latent defect on the guest side. `classify_acknowledge` recognised only the isolated test SGI and the timer PPI, so every routed device SPI fell into the `Unexpected` branch, which the exception path treats as fatal: the first real device interrupt would have panicked the kernel instead of being dispatched. A `Device(id)` arm now acknowledges, deactivates, and routes a routed SPI to its registered handler, while unowned identifiers keep the fail-closed fatal path. That fix is necessary regardless of the emulator, and it is covered by a host test.

That makes the remaining gap a property of the emulator's GICv2 model rather than of the driver, the routing, or the MSI-X programming. The ITS alternative is not reachable from this kernel either: a `gic-version=3,msi=its` machine makes the GICv2 boot path panic on the redistributor layout, so exercising interrupt-driven completion would require porting the ARM64 interrupt path to GICv3 first.

Completion therefore remains polled, and the wait's interrupt branch is present but unexercised. The driver-side work is done and correct; what remains is either a QEMU-side GICv2 fix or a GICv3 port of the ARM64 interrupt path.

One consequence is a portability constraint in the test tooling rather than in the driver. `msi=gicv2m` is a diagnostic aid for this investigation, not a boot requirement, and the property only exists on newer emulators: QEMU 8.2 — the version CI installs on Ubuntu 24.04 — has no `msi` property on `virt` at all and refuses to start with `Property 'virt-8.2-machine.msi' not found`. Because the earlier tooling appended `msi=gicv2m` unconditionally, every ARM64 CI job failed at launch while the same command passed locally on QEMU 11. `qemu_command` now probes the target machine's own property list via `-machine <type>,help` and appends the property only when the local emulator actually offers it, failing closed to the plain machine string when the emulator is missing, unusable, or lacks the property. The guest boot path is unchanged either way, because the guests were already running with the default `auto` MSI controller before the diagnostic property was added.
